# C1 分卷备份 · C4 恢复快照 — 兼容方案（只出方案，等确认）

> 2026-11-13。本文档只是方案，**还没有实现**。C2 / C3 已在 V10.40 实现（见 agent.md）。
> 原则：任何一步失败都不能清空或改写现有手帐；旧版本 App 读到新格式时只会拒绝，不会改坏数据。

## 1. 现在的格式（V10.40）

一个 JSON 文件：

```
{ format: "little-days-backup", version: 1, createdAt,
  complete: true | false,          // V10.40 新增，可选
  missing: [{ id, kind, name }],   // V10.40 新增，只在 complete:false 时有
  state: { …整本手帐… },
  media: [{ id, kind, name, mime, data: "data:…;base64,…" }] }
```

它有三个限制：

- 媒体总量超过 100 MB 就**完全不能备份**。按图库照片外推约 600 张，iPhone 实拍估计只有 300–500 张。
- base64 让体积膨胀约 33%。整个文件要在内存里拼成一个字符串，手机上可能内存不够。
- 恢复是「整份替换」，替换之前没有留一份当前手帐的副本。

## 2. C1 分卷备份（建议方案）

### 2.1 格式：一组文件，不改单文件格式

| 文件 | 内容 |
|---|---|
| `Little-Days-Backup-2026-11-13-part1of3.json` | `format`、`version: 2`、`set: { id, part: 1, parts: 3 }`、完整的 `state`、全部文件的清单 `manifest: [{ id, kind, size, sha256, part }]`，以及第 1 卷的 media |
| `…-part2of3.json`、`…-part3of3.json` | 同一个 `set.id`，只有自己那一卷的 `media`，不再重复 `state` |

- 每卷的 media 不超过 **60 MB**（base64 之后约 80 MB），保证手机内存能处理。
- 总量没有上限。
- `version: 2` 只用于分卷备份。媒体不超过 60 MB 时**仍然输出现在的 version 1 单文件**，旧版本照样能恢复。
- 每个文件都带 `sha256`，恢复时逐个校验，能发现文件损坏或被截断。

### 2.2 恢复规则

1. 用户一次选中同一组的全部文件（iOS 文件选择支持多选）。
2. 先检查同一组的卷数齐不齐、清单和校验和对不对。
   - 缺一卷：列出缺哪一卷，不开始恢复。
   - 卷数齐全：先把全部媒体写入一个新的临时区，全部成功后再进入 C4 的替换流程。

### 2.3 兼容性

| 场景 | 结果 |
|---|---|
| 旧 App 打开 version 2 文件 | 旧代码检查 `version !== 1` 后拒绝，「恢复失败」，什么都不改 ✅ |
| 新 App 打开 version 1 文件 | 照旧恢复 ✅ |
| 新 App 打开 V10.40 不完整备份（`complete:false`） | 照旧恢复，缺失的文件保留原位置 ✅ |

### 2.4 需要确认的点

- 「每卷 60 MB」是按内存估计的，需要在真机上用 300 张实拍照片测一次，确认不会崩溃。
- iOS 外壳目前把每个下载文件单独弹一次分享面板。分卷时会弹 N 次，体验差。可选的改法：
  - 原生侧把多个文件打包成一个文件夹再分享（需要改 Swift）；
  - 或者网页侧一次只导出一卷，导完一卷提示「继续下一卷」。

  **建议先用后者**，不改原生代码。

## 3. C4 恢复前快照（建议方案）

### 3.1 流程

1. 用户选择备份文件，先**完整校验**：格式、`validateStateSnapshot`、媒体齐全（或已声明缺失）。不通过就停止，现有数据不动。
2. 把**当前手帐的 JSON** 写入 IndexedDB `little-days-meta` 的新键 `little-days.v1.before-restore`，附带时间。
   - 只存文字数据，不复制媒体；媒体本来就留在 media 库里，恢复不会删除旧媒体。
   - **写入成功才继续**。写入失败就停止，并提示「先导出一份当前手帐的备份」。
3. 把备份中的媒体写入 media 库。新 id 不会覆盖旧 id，所以旧照片仍然在。
4. 用 `store.update` 一次性替换手帐（现有逻辑）。
5. 设置里出现「撤销刚才的恢复（{时间}）」，保留 7 天或直到下一次恢复：
   - 点了之后，再次确认，然后把快照写回；
   - 写回之前，先把「恢复后的手帐」也存成一份快照，所以撤销本身也可以撤销。

### 3.2 为什么这样做是安全的

- 快照只是 IndexedDB 里一个新键，不改变 `little-days.v1` 的格式；旧版本 App 会忽略它。
- 恢复从来不删除媒体，所以撤销以后旧页面的照片仍然能显示。
- 每一步失败，都停在「替换之前」：只有第 4 步会改动手帐本身，而第 2 步已经留好了退路。

### 3.3 成本与风险

- 一份快照约等于一本手帐的文字数据（几 MB）。只保留最近一份。
- 没被引用的媒体会越积越多，因为恢复之后旧媒体还在。以后可以加「清理没人用的文件」，但必须由用户手动执行，**本方案不做自动清理**。

## 4. 建议顺序与工作量（估计，未实施）

| 步骤 | 内容 | 估计 |
|---|---|---|
| 1 | C4 快照 + 撤销：改动小、立刻降低风险 | 1–1.5 天 |
| 2 | C1 分卷导出与恢复（只改网页，逐卷导出） | 2–3 天 |
| 3 | 真机：300 张实拍照片分卷导出 → 换一台设备（或删除后重装）恢复 → 核对 | 需要 iPhone |

## 5. 需要你确认

1. **分卷大小**：60 MB 一卷可以吗？更小更稳，但文件更多。
2. **iOS 导出方式**：先「逐卷导出」（不改原生），以后再考虑原生打包，可以吗？
3. **快照保存期**：快照保留 7 天、只留最近一份，可以吗？
