## 2026-11-14 · V10.46 · P0 TestFlight：手绘画完无法退出 / 选中 / 保存

**报告**：用户在真实 iPhone（TestFlight，0.1.0 (1)）上测试手绘：可以画，但画完后页面无法选中或操作，没法顺利保存。

**调查范围**：完整流程，从进入手绘 → 画 → 完成 → 回到 Studio 选中、移动 → 保存 → 阅读器 → 再次编辑。
- **网页**：Chromium 模拟 iPhone 13 + 触摸。
- **iOS 模拟器**：Debug 构建，用 XCUITest 发送**真实触摸**（按下、拖动、抬起都经过 iOS 触摸系统）。另有一个只读探针，每 200 ms 把页面状态写进无障碍标签：画板是否打开、选中的是什么、手指按下和抬起的次数。测试工程只放在 `/tmp` 的副本里，没有改仓库里的 Xcode 工程。

结果是**四个互相独立的问题**，分开记录：

### A. 画板的「取消 / 完成」在 iPhone 状态栏下面，点不到 → 卡在画板里（TestFlight 上的直接原因）

- **现象（模拟器，真实触摸）**
  - 画完点「完成」后，页面一次按下事件都没收到（按下次数停在 3 次）。
  - 画板一直开着，草稿里没有手绘图层。之后所有点击都落在画板里。
  - 截图：「取消」在时间后面，「完成」在电池图标后面。
- **根因**
  - 画板在手机上占满整个屏幕（`height: 100dvh`）。底部留了 Home 指示条的位置（`safe-area-inset-bottom`），顶部却没留状态栏的位置（`.draw-top { padding: 10px 14px }`）。
  - iOS 会把状态栏区域的点按留给系统，所以这两个按钮点不到。
  - 网页预览没有状态栏，所以网页上一直正常。
- **修改**：`Public/styles.css` 里的 `.draw-top`，上边距改为 `calc(10px + env(safe-area-inset-top))`。
- **验证（模拟器，真实触摸，同一个测试脚本）**
  - 修复后，点「完成」→ 画板关闭，出现手绘图层。
  - 点笔画能选中（出现「接着画」工具）。
  - 拖动能移动（移动了 30 pt）。
  - 点「完成」保存 → 进入阅读器，已保存的手绘有 1 个。
- **排除的猜测：「幽灵手指」**。我曾怀疑手指抬起的事件丢失，导致后面的单指点击被当成双指。真实触摸下按下和抬起始终一一对应，所以这个猜测被排除，相关代码没有改。

### B. 手绘透明的部分挡住下面的照片 / 文字 / 贴纸（任何设备都会出现）

- **现象（网页）**
  - 一张手绘是一张图片，大小等于「画到的最外边」围成的方框。
  - 两笔离得远时，这个方框盖住大半页（图层宽高超过 60%）。
  - 方框下面的文字点不到，点了会选中手绘。
- **根因**：图层元素整个方框都接收点击，包括透明的地方。
- **修改**：`Public/app.js` 的 Studio 按下事件处理。
  - 按下的位置如果落在手绘上，先查手绘在这一点约 14 px 范围内有没有笔画。
  - 每张手绘只在第一次时读一次透明度，最长边缩到 400 px，存起来重复用，旋转、缩放都算进去。
  - 没有笔画时，这次点击交给下面的照片、文字或贴纸；下面什么都没有时，仍然选中手绘。
  - 透明度读不到时，保持原来的行为。
- **验证（网页 v145）**
  - 点被手绘方框盖住的文字 → 选中文字。
  - 点笔画 → 选中手绘。

### C. 「取消」会直接丢掉新画的笔画

- **修改**：`Public/js/draw.mjs` 新增可选参数 `confirmDiscard`。
  - 有新笔画时点「取消」，或用系统返回 / Esc 关闭，会先用页面内的确认框问一句。
  - 没有新笔画时直接关闭。
  - 接着画以前的手绘时点取消，原来的手绘不变（`mediaRef` 和位置都不变）。
- **验证（网页 v145）**：确认框里选「取消」→ 留在画板；选「确定」→ 只丢掉新笔画。

### D. 手绘保存失败时直接丢失

- **修改**：`Public/app.js` 的 `drawOnPage`。写入媒体失败时，画好的内容留在内存里，用确认框问「再试一次吗？」。
- **验证（网页 v145）**：模拟第一次写入失败（设备空间已满）→ 出现重试问题 → 选「确定」→ 保存成功。

### 修复后在 iOS 模拟器里的完整验证（真实触摸，`tools/mac/uitest/DrawUITests.swift`，先删除再安装 App）

## 2026-11-14 · V10.47 · P0 TestFlight：删掉所有页面后留下一张删不掉的封面（Bug 2）+ 页数不一致（Bug 3）

**报告**：一天里把页面一张张删掉，最后剩下一张「封面」，没有删除按钮；而且删掉的页面在阅读器 / 日历里还在。页数在不同地方显示不一样。

### Bug 2 · 根因（两个，都已确认）

1. **页面目录永远画一行「封面」**（`renderPagesManage`）：就算这一天根本没有封面内容，也画一个空的占位行，而且这一行没有删除按钮。用户看到的「删不掉的封面」其实是这个占位行。
2. **删除只改了草稿，保存时又拒绝保存空的一天**：在 Studio 里删页只改编辑中的草稿；点「完成」时，`editorIsEmpty()` 为真就只提示「还没有内容」、不写入。于是已保存的那一份仍然留着被删的页面，阅读器 / 日历 / 书架照旧显示它们，重启后又「回来」。

### Bug 2 · 修改（`Public/app.js`，最小改动，不改数据格式）

- 页面目录：只有这一天**真的有封面内容**时才显示封面行（可编辑、隐藏、删除）；没有页面时显示「这一天还没有页面」。
- 删除**最后一页**（页面目录 🗑、页面 ⋯ 删除、阅读器 ⋯ 删除）或**最后一张封面**：先用页面内确认框问「删除这一页后，这一天将没有记录。」（取消 / 删除），确认后 `clearDay(date)` 把这一天的已保存记录和草稿一起删掉，回到日历的这一天（空状态）。
- 之前卡住的状态（已保存有页、草稿是空的）：点「完成」会问一句，确认后同样清空这一天，不再只提示「还没有内容」。
- **可以撤销**：清空前把这一天的已保存记录和草稿原样存到 `little-days.cleared-day`（只存最近一次）；提示条上有「撤销」，日历那一天也有「恢复刚删除的这一天」。只有删除最后一页时才会清空，其他日期不受影响。
- 旧版本自动生成的封面：保留、照常显示在页面目录里，用户自己决定隐藏或删除；不批量清理。

### Bug 3 · 页数一致

- 阅读器、日历、书架、PDF 自 V10.42 起已经用同一规则（`Public/js/pages.mjs`：封面只在显示时算一页）；备份导出全部数据，不涉及计数。
- **不一致的地方是 Studio**：标题「第 n 页 / 共 m 页」只数 Moment，不算显示中的封面；退出面板算了封面但没管它是否被隐藏。现在两处都用同一规则（`hasDayPageContent && dayCoverHidden !== true`）。
- 「篇」只剩社区 / 示例文字里，不是手帐页数。

## 2026-11-14 · V10.49 · TestFlight：「这本书的音乐」的音量滑块在 iPhone 上没有用

**报告**：用户在 iPhone（TestFlight）上拖动音量滑块（截图显示 25%），音乐的大小没有变化。

**根因**：iOS 上网页的 `<audio>.volume` 不起作用，音乐始终按最大声播放；Apple 规定网页不能直接改媒体音量。原来的代码只设置 `audio.volume`，所以滑块数字会变，声音不变。网页预览（桌面浏览器）里一直正常，所以之前没发现。
- **模拟器里的发现**：模拟器的 WKWebView 设 0.4 读回来也是 0.4，看起来像生效了。所以不能只靠「读回来是不是 1」来判断，否则真机上仍然没用。

**修改**（`Public/js/music.mjs`，`app.js` 不变）
- 在 iPhone / iPad 上（另外，任何读回来不对的浏览器也算），背景音乐改为经过 Web Audio 的增益节点（GainNode），滑块调的是增益。
- 点播放那一下就建立音频环境（不等下载完）；只有环境真的开始运行后才把 `<audio>` 接进去，所以不会因为 iOS 还没启动音频环境而没声音。
- 有 `navigator.audioSession` 时设为 `playback`，静音开关不会让音乐消失（和原来一样）。
- 接好后在 `<audio>` 上标 `data-gain="1"`，方便测试确认。
- 桌面浏览器不变，仍然直接用 `volume`。
- 视频导出里的音乐音量是另一条路径（`export.mjs`），没有改动。

**验证**
- **网页**：新增 `tests/v147-browser.cjs`，3 组通过：
  - 模拟 iOS 忽略音量：走增益，40% → 15% → 0% 增益跟着变；
  - iPhone 但读回来正常（像模拟器）：仍然走增益；
  - 桌面：不变。
  - v59（书的音乐与音量记忆）通过。
- **iOS 模拟器（真实触摸）**：`testMusicVolume`。书架 → 点书脊 → 打开书 →「给这本书配音乐」→ 点播放：在播放，并且走增益。拖动滑块 70% → 0% → 100%，音乐一直在播。**通过。**
  - 测试中顺带发现：iOS 的滑块只能拖圆点，点轨道不会跳过去（系统行为，不是 bug）。
- **模拟器测不了真实的声音大小**；真机要听一下。

### 仍需在真机（TestFlight）上确认

1. 打开一本书 →「给这本书配音乐」→ 点播放 → 把滑块拖到最左：声音变小直到听不见；拖到最右：恢复。
2. 关掉 App 再打开，音量保持上次的位置。
3. 打开静音开关时，音乐和以前一样仍会播放。

### 回退

`git revert` 这一次的提交（`ba6aa2e`）即可。数据没有变化。

## 2026-11-14 · V10.50 · P0 TestFlight：语音日记播放无声 + 视频第一次导入失败（media-timeout）

### A. 语音日记保存后播放没有声音

**排查过程**（模拟器用真实麦克风和真实点按；工具在 `tools/mac/uitest/voice-check.js`、`testVoiceFormats`）

| 检查 | 结果 |
|---|---|
| App 选用的录音格式 | iOS 18.7 的 WKWebView 选 `audio/webm; codecs=opus`（排在第一位并且支持）；`audio/mp4` 也支持 |
| 录下的数据是否有效 | 两种格式都能解码：3.1 秒，音量 RMS 约 0.12，是真实声音 |
| 文件、引用和播放 | 保存进 IndexedDB 并读回校验；页面引用 `media:<id>`，用 blob URL 播放；真实点按后 `playing` 触发、`currentTime` 在增加：**模拟器里能正常播放** |
| 重新打开后 | 模拟器关掉 App 再打开也能播放（`testVoiceRecordPlay`） |

**结论**
- 文件、格式、引用、桥接都**没有问题**：没有删除、覆盖或释放临时文件，WebView 和 Swift 之间也没有原生音频文件的桥接（录音在网页里完成，存进 IndexedDB）。
- 真机上无声，最可能的原因是**音频会话**：用过麦克风后，WebKit 让会话停留在「录音+播放」（play-and-record）。这种模式默认从**听筒**出声，音量很小，像没声音。
- 模拟器总是从 Mac 扬声器出声，**复现不了**，所以这一点要在真机上确认。

**另外发现的「假成功」**：页面上的播放状态在 `play` 事件就切成「正在播放」，也就是刚请求播放的时候，不是真正出声的时候。文件加载不了时，按钮会显示正在播放，但实际没有声音。

**修改**
- `Public/app.js`：
  - `setAudioSession()`：录音前切到 `play-and-record`；停止、出错、拒绝权限后切回 `playback`；每次播放前（不在录音时）也切到 `playback`。用的是 iOS 17+ 的 `navigator.audioSession`。
  - 播放状态只在真正的 `playing` 事件出现；`pause`、`ended`、`error`、`emptied` 时清除。
  - 播放失败会提示，并在本地日志记 `media_play`（stage、err）。
- **静音开关**：`playback` 模式不受静音开关影响（和以前媒体播放一样）。
- **蓝牙**：`playback` 支持蓝牙耳机。录音期间是 `play-and-record`。

### B. 录音状态（Phase A）

**以前**：一个「录音 / 停止」按钮，加一行很小的「正在录音 N 秒」。停止后要等录音交出最后一段数据、写入 IndexedDB、再读回校验，这段时间（你看到的约 3 秒）屏幕上没有任何反馈。

**现在**（`Public/js/personal-ui.mjs` `voiceRecorderHTML`，放在「声音与影像」面板的最上面）：

| 状态 | 显示 |
|---|---|
| 准备 | 「开始录音」按钮；麦克风权限提示（用 `navigator.permissions` 读取，不会弹出询问） |
| 录音中 | 声波（麦克风的实时音量，不是循环动画）；红点脉冲、「正在录音」、计时 00:12；「停止并保存」 |
| 保存中 | 点停止后马上出现「正在保存录音…」，一直显示到文件写入并读回校验 |
| 已保存 | 「录音已保存」，只在保存真正完成后才显示；可以马上播放 |
| 失败 | 「录音没有保存成功」；录音保留在内存里，可以「重新保存」或「放弃」（放弃前会确认）；有未保存的录音时不能开始新的录音 |

### C. 视频第一次导入失败（media-timeout），重试成功

**根因（模拟器上已确认）**
- iOS 外壳设置了 `mediaTypesRequiringUserActionForPlayback = .all`。这时 WKWebView **没有新的点按就不会加载**音视频的元数据。
- 导入时，`mediaMetadata()` 在选完视频后等 `loadedmetadata`，最多 10 秒，等不到就报 `media-timeout`。
- 「重试」本身是一次点按，所以第二次能成功。
- 模拟器证据（`testVideoMetadata`）：

| 外壳设置 | 不点按 | 点按后 |
|---|---|---|
| 修复前（`.all`） | 超时 | 91 ms 加载 |
| 修复后（`[]`） | 156 ms 加载 | 53 ms 加载 |

**修改**
- 外壳 `LittleDaysWebShellView.swift` 改为 `mediaTypesRequiringUserActionForPlayback = []`。App 里没有任何声音或视频会自己开始播放，都要点按。
- 网页 `mediaMetadata()`：超时不再算失败。文件照常保存（时长在播放时读取），本地日志记 `media_meta_timeout`；真正的媒体错误仍然会报错。
- 重试的路径不变，同一个文件只会保存一次（v148 第 4 组）。

**顺带修改**：外壳以前对麦克风用 `.prompt`，WebKit 每次打开 App 都会再问一次。现在 App 自己的页面直接授权，iOS 系统仍然会在第一次问。

### 数据安全回答

1. **录音什么时候真正持久化**：`attachClip` → `media.put`（写入 IndexedDB，再读回比对字节数）→ 页面引用这个文件 → `flushDraft`。「录音已保存」在这些都完成后才显示。
2. **保存中关闭编辑器**：保存期间 `busyMedia` 为真，离开编辑器会被拦下并提示（原有逻辑）。
3. **文件和引用会不会不同步**：先存文件、再写引用，所以不会出现指向不存在文件的引用。如果写引用失败，只会留下一个没被用到的文件（从不自动删除媒体）。
4. **后台或被系统终止**：
   - 切到后台会自动停止并保存。
   - **限制**：如果录音过程中 App 被系统直接杀掉，还在内存里的录音片段会丢失。录音中途分段写盘还没有做。
5. **备份与恢复**：`media.backup` 包含所有被引用的媒体，录音也在里面。v31 测试覆盖了带录音的备份和恢复。
6. **删除页面和撤销**：删除页面或清空一天都不会删除媒体文件（V10.47 的「恢复」可以找回）。
7. **重新打开后播放**：模拟器已验证（真实触摸，关掉 App 再打开）。
