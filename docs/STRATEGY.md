# Little Days · 产品战略重新定位与开发优先级（2026-11-09，已确认）

> 2026-11-09 用户已确认按本文件推进。进度：F1 Quick Create v2、F2 按照片形状自动排、F3 实验室开关 + 本机测试记录、F4 Story 分享 已完成（网页版，见 ROADMAP「V5.2」）；F5 数据可靠性、F6 原生最小闭环未开始。
> 标注说明：**[事实]** 有公开来源或仓库代码可查；**[假设]** 我们的判断，还没被证据支持；**[待验证]** 需要用户实验回答。

## 0. 先说结论

1. **最值得押注的差异化**：把用户**自己相册里的照片**一键变成好看的手帐页，并且这些页会自动积累成一本**按日期和主题整理、值得翻看的书**。也就是「照片 → 漂亮的页 → 一本书」。
   - 不靠更多贴纸，不靠社区，不靠共同手帐，也不靠记账、护肤这类结构化主题。
2. **只做三个核心功能来验证**：
   - ① 照片优先的 Quick Create：多张照片 → 自动排版 → 换一种 → 一句话，90 秒内完成；
   - ② 会长大的书：日历、书、阅读模式，加每周 / 每月自动回顾；
   - ③ 一键分享导出：Instagram Story / Feed 尺寸。
3. **最大的风险**不是「功能不够」，而是：
   - 功能已经太多；
   - 默认入口用的是图库照片（Unsplash），不是用户自己的回忆；
   - 自动排版还不认照片横竖和主体，做不到「默认就好看」；
   - 手帐需求可能是**事件型**（旅行、生日），不是**每天型**。

## 任务 A · 重新定义产品定位

### A1. 一句话价值主张

**Turn the photos you already take into a beautiful little book of your life — one page in under a minute.**

中文：把你本来就会拍的照片，一分钟变成一页好看的手帐，慢慢攒成一本属于你的生活之书。

与原文案的差别：
- 去掉了「Capture naturally」。Capture 不是我们能赢的地方，Apple Journal 已经在做。
- 落点放在「已有照片」「一分钟」「一本书」这三个可以检验的承诺上。

### A2. 核心目标用户 **[假设，待验证]**

**主要人群：18–34 岁、美国、iPhone、拍照多的女性用户。**
- 发过 photo dump 或 Story recap，喜欢 scrapbook / stationery 的审美；
- 但没有坚持过手帐（纸质或 Zinnia、GoodNotes 这类），原因是「太花时间」「不会排」。

**典型场景：**
1. 周末、旅行、聚会之后，相册里有 10–40 张照片，想留下一页「这天很好」，但不想开 Canva 慢慢排。
2. 晚上睡前，把今天 1–3 张照片配一句话。
3. 某个长期主题想单独成书：宠物、孩子、旅行、做饭、健身进度照。

**次要人群（保留但不为他们设计默认路径）：**
- 喜欢慢慢装饰的重度手帐用户。他们已经有 Zinnia / GoodNotes，Creative Mode 是留住他们的底线，但不是获客理由。

### A3. 主要痛点

| 痛点 | 判断 |
|---|---|
| 照片太多，没有被「整理成故事」，翻相册找不到当时的感觉 | **[假设]** 很普遍，但用户不一定为此行动 |
| 想要漂亮的作品，但排版、挑贴纸、选字体太累 | **[假设]**，这是我们的核心赌注 |
| 写长日记有压力，坚持不下来 | **[事实]** 日记类产品普遍面临这个问题（Apple Journal 用建议和连续天数去缓解） |
| 发到 Instagram 的内容不是为自己保存的，而且会被平台节奏淹没 | **[假设]** |

### A4. 与竞品的实质差异（诚实版）

- **vs Zinnia**：我们是「照片进 → 页面出」，它是「空白页 / 模板 + 手动装饰 + 计划」。
  - 差异**只有在自动排版真的好看时才成立**。现在代码里的自动排版只按照片张数选版式，不认横竖、不认主体（见任务 F），所以这个差异**目前还没做出来**。
- **vs Day One / Apple Journal**：它们是「文字为主、媒体附带」，我们是「视觉页面为主、文字一句话」。
  - 输出物不同：它们产出时间线，我们产出**一本书的页**。
- **vs Shuffles / Canva / CapCut**：它们产出一次性作品，我们的作品**按日期和主题累积**，可以回看、成书。

### A5. 最容易被复制的部分

- 贴纸、字体、纸张、杂志封面、颜色主题：素材谁都能加。
- 「照片 + 一句话」单页形式：Apple Journal 加一个版式就能做到。
- 共同手帐：Day One 已经免费提供。

### A6. 最可能形成长期优势的部分

1. **用户自己积累的书**：内容越多，迁移成本越高。这是所有日记类产品真正的护城河。
   - 前提是**数据可靠**；一旦丢数据，护城河立刻变成差评。
2. **「默认就好看」的排版品味与布局引擎**：认横竖、认主体、配色跟着照片走、可以「换一种」。
   - 难的不是代码，而是**持续的设计品味和大量真实照片的调教**，这比素材难复制。
3. **从「页」自动长成「书」的回顾体验**：每周 / 每月自动拼成跨页、年度书。

## 任务 B · 五个最重要的风险

| # | 风险 | 为什么严重 | 具体验证方法 |
|---|---|---|---|
| 1 | **功能已经过多，核心路径被稀释** | 现在已经有：社区演示、私信、好友、等级 / 经验、装扮空间、通知中心、协作演示、12 套主题字段、记账字段、6 种杂志封面、9 种纸张、颜色主题、视频导出、手绘、照片编辑器、本地登录。新用户第一次打开时，「把照片变成页」这条路要经过「＋ → 选方式 → 选书 → 开始 → 选图」，而且自己的多张照片只能走「其他 → 自由排版」，还会被照片编辑器逐张打断。 | 让 5 位从没用过的目标用户在无提示下「用自己 5 张照片做一页」，记录完成率、时间、点击次数，以及第一次卡住的位置。**标准**：中位数超过 3 分钟或完成率低于 80%，就说明入口必须先精简，然后才能谈留存。 |
| 2 | **记录习惯难建立，需求可能是事件型** | 手帐和 scrapbook 很可能集中在旅行、生日、节日（**[假设]**）。如果是这样，「每天都来」的设计（连续天数、等级）方向就错了。 | 在 30 天实验里看「有记录的天」的分布：如果超过 60% 的页集中在少数事件日，而平常日几乎没有，就说明是事件型，定位应改为「旅行 / 里程碑相册书」，并用回顾和事件提醒来留存，而不是用连续天数。 |
| 3 | **自由编辑和操作简单互相拖累** | 每加一个自由编辑能力（图层、裁切、形状、手绘），默认界面就多一个按钮。现在写作页同时有页面条、方式条、页面细栏、撤销 / 重做 + 5 个添加按钮、9 个工具 dock。 | A/B（两组各 8 人）：A 组 Quick Create 结果页只显示「换一种 / 写一句 / 完成」；B 组显示现有完整工具。比较完成时间、满意度，以及 7 天内主动进入编辑的比例。**如果 A 组满意度不低于 B 组、且完成更快**，就把完整工具收进「编辑」二级页面。 |
| 4 | **主题过多导致定位模糊** | 记账、护肤、学习这类结构化记录，用户会拿去和专门的 tracker 比（Notion、记账 App、Apple Health）；我们赢不了，还会把产品拉成「效率工具」，违背「不做传统效率工具」的产品原则。 | 实验中只提供 4 个主题书（旅行、美食 / 食谱、宠物 / 孩子、健身），加「自定义」。统计：用户建了哪种书、每本书 30 天内有几页、字段是否被填写。**标准**：字段填写率低于 30%，或除默认书以外的书少于 3 页，就说明结构化字段不值得继续扩展。 |
| 5 | **竞品已覆盖主要需求，用户没有换的理由** | Apple Journal 免费、预装、能从照片生成建议；Zinnia 素材多；Day One 有共享。用户最可能的反应是「挺好看，但我已经在用相册 / Notes / IG 了」。 | 在第一次访谈和第 30 天访谈中都问：「如果明天 Little Days 消失，你会用什么替代？」以及「你会不会失望？」（很失望 / 有点 / 不会）。**标准**：「很失望」的比例低于 25%，就说明差异化不够强，需要回到定位层面调整，而不是继续加功能。这里的阈值是我们自己设的目标，不是行业基准。 |

另外补充两个工程风险（不在前五，但会直接毁掉「值得长期保存」这个承诺）：
- **数据可靠性**：目前照片、视频、录音都在 WKWebView 的 IndexedDB 里，只能手动导出备份，没有云同步。iOS 在存储紧张时会不会清理 WKWebView 的数据，**[待验证]**，必须在真机上测。
- **原生能力缺失**：没有经过验证的 Xcode 构建和 TestFlight；Swift 外壳还没有 PhotoKit（今天拍的照片、拍摄时间 / 地点）、系统分享、通知、小组件的桥接。最核心的差异化（自动拿到今天的照片）依赖这些。

已实现的功能不删除。标「Pause」的意思是：**停止扩展，测试版默认隐藏到「实验室」里**。

### Must Have（验证核心假设）

| 功能 | 现状 | 为什么 | 验证的假设 |
|---|---|---|---|

## 任务 D · 核心用户旅程

目标：减少操作步数，缩短完成时间，默认就好看，保存可靠。下面写的点击数是**目标值**，不是现状。

### D1. 首次使用（目标：从打开到完成第一页，3 分钟以内，最多 6 次点击）

1. 打开 App：一屏说明「把你的照片变成一页手帐」+「选几张照片」大按钮。**不要登录，不要导览，不要选主题。**
2. 系统照片选择器：选 3–8 张（打开时优先显示今天 / 最近的照片）。
3. 自动生成页面：纸张颜色从照片里取，排版认横竖和主体；下面三个按钮：「换一种」「写一句话」「完成」。**不弹照片编辑器。**
4. 写一句话（可以跳过）→ 完成 → 「已放进《我的日常》」，同时给两个选项：分享 / 再做一页。
5. 第一次完成后，才轻提示：「想把旅行单独成一本吗？」

**现状对比（网页版，事实）**
- 自己的单张照片：＋ → 照片+一句话 → 我的照片 → 开始 → 选图 → 写字，约 6 步，只能放一张。
- 自己的多张照片：＋ → 其他：自由排版 → 照片 → 相册 → 选多张 → **照片编辑器逐张打开** → 版式自动，约 8 步以上，中途还会被打断。
- 第一次使用还要先经过本地登录和导览。

### D2. 日常使用（目标：30 秒，最多 4 次点击）

- 晚上收到提醒（原生，可关闭）：「今天拍了 6 张照片，留一页吗？」→ 打开就是预选好的照片 → 自动成页 → 写一句 → 完成。
- 没有照片的日子：＋ → 随手写 → 写一句话。
- 一天可以有多页，页面条上显示「封面 + N 页」（已完成）。
- **不做连续天数惩罚**：漏几天没有关系，回顾页只展示有记录的日子。

### D3. 深度创作

- 在 Quick Create 结果页点「编辑」，才进入完整工具：图层、贴纸、字体、纸张、手绘、照片编辑。
- 完整工具**不出现在默认路径上**。
- 从自动版式切到自由编辑时保留位置，只有在「重新自动排版」时才需要确认（已有确认）。

### D4. 长期回顾

- 日历：每个有记录的日子显示缩略图（照片墙已有）。
- 书架 → 书 → 按月翻页，每月自动生成一个「本月」跨页（待做）。
- 某一天阅读页：视频、音频直接播放（已完成）。
- 「一年前的今天」放在首页一角（待做，成本低，留存价值高 **[假设]**）。

### D5. 成长记录

- 不做成表单 App。主题书里每一页仍然是「照片 + 一句话」。
- 健身书可以多一个可选的小字段行（例如「深蹲 60kg × 5」），**不强制填写**。
- 打卡与感想保留现有实现；回顾时以「进步照片墙」呈现（例如同一动作的照片按时间排开），而不是图表。

### D6. 未来的共同创作（先测需求，不先做实时协作）

> 2026-11-09 更新：用户同意「一个人记，其他人看」更可能是真实情况。已实现第一步的替代方案：整本书分享成 PDF（V5.4），并在分享后用诚实的意向问题测「想让家人也能加照片」的比例（本机测试记录 `contribute_interest`）。30 天实验招募时，约一半选情侣或新手父母，对比他们的留存和分享率。

- **第一步（不写服务端代码）**：「只读分享一本书」——导出这本书为网页或 PDF，发给朋友看。
- **第二步（低成本测投稿）**：给朋友一个「往这本书投几张照片」的链接，照片由书的主人确认后才放入（异步，不需要对方注册）。
- **第三步**：真正的共同编辑。按页加锁，异步合并，**不做实时协作**。
- 你问「是否应该先做异步而不是实时」：**是**。共同手帐属于事件型（旅行、婚礼、宝宝），一次只需要几个人各自加几页，实时协作的复杂度换不来价值。

## 任务 E · 30 天用户验证计划（个人创业者可执行）

### 前置条件（第 0 周）

- 测试版本二选一：
  - **TestFlight**（推荐，需要一台 Mac 构建，能测通知和照片权限）；
  - 或把网页版部署成公开的静态网站，让测试者「添加到主屏幕」使用。
- 现在的在线链接是私人的，不能直接给测试者用。
- 网页版在 iOS Safari 下的存储清理规则 **[待验证]**；用网页版就要提醒测试者导出备份。
- 测试版隐藏 Pause 列表中的模块，只保留：Quick Create、随手写、书、日历、分享导出、Creative Mode（作为二级入口）。
- 加上本机事件记录（不上传）+「导出测试日志」按钮，在知情同意下由测试者发回。

### 招募 15–20 名美国目标用户

- **渠道**：
  - r/scrapbooking、r/Journaling、r/bulletjournal 等社区（遵守各版规，先问版主）；
  - TikTok / Instagram 上 #photodump、#scrapbookjournal 的小创作者帮忙转发；
  - 美国朋友的朋友；
  - 如有预算，可用付费用户访谈平台。
- **筛选问卷**：
  - iPhone 用户；
  - 每周拍照 ≥10 张；
  - 过去一年发过 photo dump 或 Story recap；
  - 试过手帐但没坚持，或者想做但觉得太费时间；
  - **排除**设计师和重度手帐爱好者，最多各留 2 人作对照。
- **报酬**：首次访谈 + 第 30 天访谈给小额礼品卡。日常使用不给钱，否则留存数据失真。

### 第 1 天：第一次手帐（远程 30 分钟，主持但不帮忙）

- 任务：「用你最近一次出门的照片做一页」。
- **记录**：完成率、完成用时、点击次数、第一次卡住的地方、是否主动点「换一种」、是否手动调整排版。
- 当场问两个问题（1–5 分）：「你会把这页留下吗？」「你会发给别人看吗？」

### 第 1–30 天：自然使用

- 不催促、不发每日任务；只用产品本身的提醒（如果有）。
- 第 7 天发一次简短问卷（3 题）。
- 第 30 天做 20 分钟访谈。

### 指标与目标（我们自己设的门槛，不是行业基准）

| 维度 | 怎么量 | 继续的信号 | 必须调整的信号 |
|---|---|---|---|
| 上手 | 第一页完成率、中位用时 | ≥80% 不需要帮助就能完成；第二页中位数 ≤90 秒 | 完成率 <60%，或中位数 >3 分钟 |
| 默认就好看 | 「会留下」评分；自动排版后手动改动的比例 | ≥70% 打 4–5 分；≤30% 的页被手动重新排 | <50% 打 4–5 分，或大多数页被重排 |
| 7 天留存 | 第 2–7 天里至少 1 天新增或查看过页面 | ≥40%（20 人中约 8 人） | <20% |
| 30 天留存 | 第 4 周仍新增 ≥1 页 | ≥20–25%（约 4–5 人） | ≤10% |
| 使用模式 | 有记录的天的分布 | 平常日也有记录 | >60% 的页集中在少数事件日 → 转为「事件 / 旅行相册书」定位 |
| 主动分享 | 在**没被要求**的情况下用系统分享导出过页面 | ≥30% 的人至少分享 1 次 | <10% |
| 主题书价值 | 建了非默认书的人数、每本书的页数、字段填写率 | ≥40% 的人建了主题书，且这本书 ≥3 页 | 主题书几乎都空着，或字段填写率 <30% |
| 产品不可替代性 | 「如果消失你会很失望」的比例 | ≥40% | <25% |
| 共同创作需求 | 访谈中自发提到「想和某人一起做」 | ≥30% 自发提到 | 几乎没人提 → 继续放在 Later |

### 判读规则

- **上手和默认好看都不过关**：问题在核心体验。先修 Quick Create 和排版，暂时不要看留存。
- **上手好，但 7 天留存低**：作品有价值，但缺少回来的理由。优先做提醒、回顾和「一年前的今天」。
- **留存集中在事件日**：转向「事件 / 旅行相册书」定位，用事件触发和回顾留住人，放弃每天型的设计。
- **分享率高、留存低**：它更像一个「做图工具」。要么接受这个定位（转向 CapCut 模板赛道，竞争很激烈），要么加强「成书」的价值。

## 任务 F · 下一阶段开发建议（基于仓库现状）

### 现状盘点 **[事实，来自代码]**

**已经有的**（网页版，Linux + Chromium 测试通过；iOS / Windows 真机都没有验证）：
- 记录面板：照片+一句话 / 随手写 / 手绘；
- 一天 = 封面 + 页，页面条和「整理这一天」；
- 自由图层（照片、文字、贴纸、视频、音频、手绘）；
- 按张数选的 5 种左右版式 + 空相框；
- 照片编辑器；日历照片墙；某一天阅读页（音视频播放）；
- 书、杂志封面；Growth；PNG / 视频导出；本机备份 / 恢复；
- 社区、协作、装扮的本机演示。

**关键缺口：**
1. `Public/js/day.mjs` 的 `autoLayout(count, template, region)` 只看**张数**，不看照片的宽高和主体，裁切固定从中心开始。
2. Quick Create 的「照片+一句话」只支持单张照片，默认推荐的是 **Unsplash 图库照片**（「今日照片」）。图库照片不是用户的回忆，适合当背景，不适合当默认入口。
3. 新照片默认会打开照片编辑器（`handleImageUpload` → `editPhotos`），打断快速流程。
4. 没有 9:16 导出，没有系统分享调用。
5. 没有事件记录，30 天实验无法量化。
6. Swift 外壳没有 PhotoKit、分享、通知的桥接，也没有经过验证的构建。
7. 首次启动要先经过本地登录和导览。

### 建议的开发任务（按顺序，需要你确认后再做）

**任务 1：Quick Create v2（照片优先）**
- 记录面板默认选中「照片」，并把「从我的相册选几张」作为第一选项；图库照片改成「背景 / 灵感」，降到次要位置。
- 多选 1–10 张自己的照片 → 自动生成页面 → 结果页只显示「换一种」「写一句话」「编辑」「完成」。
- Quick Create 路径里**不自动打开照片编辑器**（编辑入口仍然保留）。
- 预计改动：`Public/app.js` 的 `startQuickRecord` / `handleImageUpload` 增加 quick 目标；新增结果条。
- 测试：新增 v52 浏览器测试。
- 验收：从「＋」到完成 ≤6 次点击；导出效果和页面一致。

**任务 2：认横竖和主体的自动排版**
- 媒体元数据保存原图宽高（`media.put` 的 metadata 里增加 w/h）。
- 版式模板改为「槽位 + 可接受的宽高比范围 + 权重」。
- 选版式时打分：裁切损失、主图大小、留白平衡，取前 3 个作为「换一种」的候选。
- 裁切焦点：网页版先用中心加人脸检测（浏览器有就用，没有就居中）；原生版之后用 Vision 显著性区域，通过桥接传回。
- 纸张或胶带颜色从照片主色中选（只在现有调色板里取，保持文具店风格）。
- 数据模型：photo layer 增加可选字段 `focus {x, y}`、`sourceAspect`，Swift 端加可选字段，Core 测试同步。
- 验收：横竖混合的 3 张或 5 张照片不出现严重裁切；单元测试覆盖打分函数。

**任务 3：测试版精简 + 事件记录**
- 增加 `features.labs` 开关：社区、私信、等级、装扮、协作演示、本地登录、颜色主题默认隐藏，**不删除代码、不动数据**。
- 本机事件记录（localStorage 中的环形缓冲，不上传）：
  - 记录：`quick_start`、`page_done`（含用时和点击数）、`layout_shuffle`、`layout_manual_edit`、`export`、`share`、`book_create`、`day_view`；
  - Settings 里加「导出测试日志」。
- 验收：测试版首页只有核心入口；日志可以导出成 JSON，并且不包含任何内容文字或图片。

**任务 4：分享导出**
- 导出尺寸增加 9:16（Story）：页面居中，上下用纸色或照片模糊填充。
- 网页版用 `navigator.share`（不支持时退回下载）；原生版通过桥接调用系统分享面板。
- 可选的小水印「made with Little Days」，默认开启，可以关闭。

**任务 5：数据可靠性**
- 网页版启动时调用 `navigator.storage.persist()`。
- 备份提醒：例如 14 天未备份且有新页面时，温和提示。
- 在真机上验证 WKWebView 的 IndexedDB 是否会被系统清理，并把结果写进文档。
- 原生方向：把媒体文件迁移到 App 沙盒文件，再做 iCloud 备份（单独确认，属于较大改动）。

**任务 6：原生最小闭环（需要 Mac）**
- Xcode 构建 → TestFlight。
- 桥接：PHPicker 多选（带拍摄日期）、系统分享、本地通知（晚间提醒，可关闭）。
- 这是 30 天实验能否用真机版本进行的前提。

**暂缓**：社区、私信、等级、装扮、协作，以及新的素材扩展。

## 最终回答

**Little Days 当前最值得押注的差异化：**
- 用户自己的照片「默认就好看」地自动成页，并且这些页会自动积累成一本值得翻看的书。
- 让普通人不用设计、在一分钟内，把相册里的生活变成一本有连续故事的手帐。

**如果只能做三个核心功能来验证：**

1. **照片优先的 Quick Create + 有品味的自动排版**
   - 多选照片 → 认横竖和主体的自动排版 → 「换一种」 → 一句话 → 完成，90 秒内。
   - 验证：「effortless + beautiful by default」是否成立。
2. **会长大的书**
   - 日历、书、某一天阅读（含音视频），加每周 / 每月自动回顾。
   - 验证：用户是否因为「积累和回看」而回来，也就是留存和长期价值。
3. **一键分享导出**（Story / Feed 尺寸，调用系统分享）
   - 验证：作品是否「好到愿意给别人看」，同时这也是零成本获客渠道。

**不在这三个里面的**：社区、共同手帐、更多主题字段、更多素材。它们都依赖上面三个先成立，现在做只会增加复杂度。
